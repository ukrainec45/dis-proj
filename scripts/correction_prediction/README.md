# Прогнозування наслідків візуальної корекції

Окремий дослід для передпольотного планування. Код, протокол, конфігурації,
notebook, тести та нові результати зберігаються в цій папці.

**Стан: реалізована експериментальна інфраструктура; нових емпіричних результатів
ще немає.** Локальні тести синтетичні. GPU-кампанію та платні запити Jev агент
не виконував. Кількість знімків основної кампанії ще не погоджена.

## Що прогнозуємо

`Δe = e_до − e_після`, горизонтальні похибки в метрах. Позитивне значення —
покращення. За відмови зберігається prior, Δe=0; прийнята прив’язка з малою
зміною є окремим результатом. Модель повертає відмову та сім інтервалів Δe.
Майбутній кадр камери у прогноз не входить. Кадри потрібні локалізатору для
отримання навчальних відповідей, а еталон — лише симулятору prior та оцінюванню.

Це прогноз результату заміни позиції прийнятою прив’язкою. Злиття оцінок,
калібрована коваріація вимірювання, ймовірність прибуття та безпека польоту
поки не реалізовані. Усі артефакти мають `research_only=true`.

## Початок роботи

З кореня репозиторію, у локальному середовищі з основними залежностями:

```powershell
.venv/Scripts/python.exe -m pip install -r scripts/correction_prediction/requirements.txt
.venv/Scripts/python.exe -m scripts.correction_prediction --help
.venv/Scripts/python.exe -m scripts.correction_prediction pilot-config
.venv/Scripts/python.exe -m pytest scripts/correction_prediction/tests -q -p no:cacheprovider --basetemp scripts/correction_prediction/.test-tmp
```

Для реального пілота відкрийте [Colab notebook](notebooks/pilot.ipynb). Скопіюйте
цей пакет і `scripts/visibility_localization/` разом із `scripts/__init__.py`
у відповідну структуру Drive. Укажіть реальні шляхи до CSV вибірки попереднього
quick visibility запуску та даних AnyVisLoc. `CAMP_CHECKPOINT = None` означає
автоматичне використання кешу або завантаження офіційних ваг CAMP у
`correction_prediction/model_cache/`. За наявності повного checkpoint можна
натомість указати його шлях. RoMa/DINOv2 отримуються під час ініціалізації
локалізатора та також кешуються; старий notebook запускати не потрібно.
Потрібен CUDA GPU runtime; CPU-сеанс зупиняється до завантаження моделей.

Детермінований режим PyTorch зберігається. Перед імпортом/ініціалізацією CUDA
notebook задає `CUBLAS_WORKSPACE_CONFIG=:4096:8` (також підтримується `:16:8`).
`initialize_backend` перевіряє GPU-множення матриць і матриці на вектор до
завантаження ваг. Якщо CUDA вже запущено без цієї змінної, потрібен Restart
session; проста зміна os.environ після помилки не є надійним відновленням.
Параметр зберігається у manifest. Попередній pilot-v1 із 288 CuBLAS exceptions
не містить результатів локалізації; повторний запуск має новий каталог
`pilot-v2-cublas`, а старі записи зберігаються для аудиту.

Якщо pip змінив уже імпортовані NumPy/SciPy/PyTorch, комірка встановлення
вимагає `Runtime → Restart session`. Після перезапуску встановіть
`INSTALL_DEPENDENCIES=False` і виконайте notebook зверху. Помилка імпорту
`atleast_nd` усередині SciPy вказує на неузгоджені модулі; найперше слід
перезапустити ядро. Ваги CAMP через таку помилку повторно завантажувати не треба.
Notebook окремо перевіряє SciPy у своєму процесі: успішний pytest у дочірньому
процесі сам по собі не підтверджує чистоту ядра notebook.
`fixed_pilot_selection` повторює `pilot_order` попереднього досліду і бере
перші 8 кадрів: по два з Scene_05/08/11/21; випадкової заміни відсутніх немає.

Пілот: **8 кадрів × 4 σXY (5/20/50/100 м) × 3 умови × 3 повтори = 288 спроб**.
Локалізатор — CAMP + RoMa + PnP, aerial map/DSM, noisy prior та prior yaw.
Умови — clear/fog_extreme/smoke_extreme. Код, версії бібліотек, карти та ваги
фіксуються в `campaign.json`. Результат кожної спроби має SHA-256.

Після переривання повторіть запуск із тим самим каталогом: завершені спроби
перевіряються і не повторюються. Зміна джерел/коду/версій/ваг потребує нового
каталогу. Технічні помилки зберігаються, не стають відмовами локалізатора.
Пілот за замовчуванням зупиняється після першої технічної помилки та показує
повний traceback, щоб не витрачати решту 288 спроб на спільний збій.
Окремий запис залишається на диску навіть без повного dataset.json.
Вивести причини вже збережених помилок без GPU й повторного зіставлення:

```powershell
python -m scripts.correction_prediction diagnose scripts/correction_prediction/results/pilot-v1
```

Оновлена комірка аудиту notebook також показує типи винятків, частоти й
перші tracebacks. Старі каталоги не перезаписуйте; після виправлення причини
та зміни коду потрібен новий каталог запуску.

```powershell
python -m scripts.correction_prediction audit scripts/correction_prediction/results/pilot-v1/dataset.json
```

Після пілота погоджуються обсяг, території, часові набори можливостей корекції,
просторове перекриття та бюджет основної кампанії. Пілотні дані не можна
передати `run_training` як основний навчальний набір.

## Основна кампанія, навчання та Jev

### Попередні базові моделі на завершеному пілоті

Відкрийте [baseline_models.ipynb](notebooks/baseline_models.ipynb). Це окремий
CPU-notebook: він читає готовий `results/pilot-v2-cublas/dataset.json` у Drive,
не запускає локалізацію, не завантажує ваги й не викликає Jev. Оновіть пакет
цілком, включно з `pilot_baselines.py` та `reporting.py`. Стара помилка аудиту
`No module named ...diagnostics` означає відсутність відповідного файлу в
Drive, а не втрату збереженого dataset.json.

```powershell
python -m scripts.correction_prediction pilot-baselines scripts/correction_prediction/results/pilot-v2-cublas/dataset.json scripts/correction_prediction/results/pilot-baselines-v1
```

Це окрема розвідувальна процедура, яка не змінює ролі вихідних pilot-рядків
і не обходить вимоги `run_training` до основної кампанії. Частотний контроль,
регресія та ліс (geometry/map) перевіряються із відкладанням цілої просторової
групи. Для чотирьох сцен по два кадри — чотири проходи: 6 кадрів/216 спроб
для навчання й 2 кадри/72 спроби для перевірки. Перекриття різних сцен не
вважається автоматично виключеним; такі групи не є доказом незалежного
остаточного тесту.

Зберігаються OOF-прогнози, моделі кожного проходу, метрики по сценах/умовах/σ,
графік надійності сирих імовірностей і sensitivity до інтервалів. Калібрування
не навчається, гіперпараметри не підбираються, переможець не призначається.
Усі кандидати також навчаються на повному пілоті у `exploratory_models/`;
ці refits не мають незалежної оцінки й не підключаються автоматично до
планувальника. `validation_passed=false`, `final_test_evaluated=false`.

У вже переглянутому зведенні пілота: 288 спроб, 8 кадрів, 0 технічних помилок,
254 покращення, 4 погіршення, 27 відмов і 3 нейтральні зміни. Ці числа взято
із збереженого виводу notebook, а не з локально перерахованих первинних даних.
Погіршень недостатньо для сильних тверджень про їхні ймовірності; клас
harm_large взагалі відсутній. Вісім кадрів не перетворюються на 288 незалежних
випробувань завдяки синтетичним повторам.

### Основна кампанія

`campaign.run_campaign(..., stage='main', main_design=...)` потребує вибірки
з явними `split`, `spatial_group`, `opportunity_group`, точної кількості
`approved_attempts` та запису `spatial_overlap_audit` у main_design. Ролі:
`train`, `validation`, `calibration`, `test`. Спільні території не можна
розміщувати в різних частинах; групи перекриття визначає дослідник за картою.
Стара Scene_21 вже переглядалася і не є незалежним тестом.

Погоджені локальні кандидати: частотний контроль, логістична регресія та
випадковий ліс. Регресія й ліс мають окремі geometry/map варіанти.
Гіперпараметри та характеристики ознак описано в [протоколі](protocol.md).

**Jev не донавчається.** Два кандидати: лише числові ознаки та ті самі ознаки
з 256×256 фрагментом карти. API використовує Choice із вісьмома probabilities;
`confidence` не є ймовірністю успіху. За замовчуванням API вимкнено.

```powershell
# Без --max-requests читається лише точний кеш; за промаху буде явна помилка.
python -m scripts.correction_prediction jev DATASET_JSON NUMERIC_JSON --cache-dir CACHE_DIRECTORY
python -m scripts.correction_prediction jev DATASET_JSON IMAGE_JSON --with-image --cache-dir CACHE_DIRECTORY
```

Для погодженого мережевого запуску встановіть TYPESAFE_API_KEY через секрет
середовища й додайте `--max-requests N`. Це сукупна кількість зарезервованих
запитів у цьому кеші, включно з невдалими. Кеш із ключами не зберігає секрети.
Після невідомого результату API автоматичного повтору немає: це запобігає
прихованим додатковим витратам. Запит, отримана відповідь, usage та час
зберігаються. Залишений після аварії `.request.lock` треба перевірити перед
ручним відновленням. Число запитів не є лімітом вартості в грошах.

Для main dataset звичайний запуск Jev обробляє лише validation/calibration.
Пілот обробляється окремо для перевірки API. Результати обох Jev варіантів
потрібно отримати **перед** їх включенням у заморожене порівняння:

```powershell
python -m scripts.correction_prediction train DATASET_JSON TRAIN_OUTPUT --jev-numeric NUMERIC_JSON --jev-map IMAGE_JSON
python -m scripts.correction_prediction learning-curve DATASET_JSON LEARNING_CURVE_JSON
```

Без зовнішніх файлів CLI виконає лише локальні контролі; це не повне
порівняння з Jev. Калібрування — одна температура, окремо для кожного
кандидата, тільки на calibration. Конфігурація обирається за log loss на
validation. Ваги не перенавчаються після вибору, щоб зберегти відокремлення
даних калібрування. Моделі — переносні JSON, без pickle.

Остаточні прогнози Jev потребують зафіксованого run:

```powershell
python -m scripts.correction_prediction jev DATASET_JSON TEST_NUMERIC_JSON --frozen-run TRAIN_OUTPUT --cache-dir CACHE_DIRECTORY
python -m scripts.correction_prediction jev DATASET_JSON TEST_IMAGE_JSON --with-image --frozen-run TRAIN_OUTPUT --cache-dir CACHE_DIRECTORY
python -m scripts.correction_prediction evaluate TRAIN_OUTPUT DATASET_JSON TEST_OUTPUT --jev-numeric TEST_NUMERIC_JSON --jev-map TEST_IMAGE_JSON
python -m scripts.correction_prediction opportunities TRAIN_OUTPUT DATASET_JSON TEST_OUTPUT OPPORTUNITIES_JSON
```

Після відкриття тесту його більше не можна називати новим незалежним тестом
для зміненого методу. Код дозволяє лише окремі незмінні каталоги результатів;
дотримання наукового протоколу також потребує журналу рішень дослідника.

Звіти містять метрики, `report.md`, `calibration.png`, sensitivity до
укрупнення інтервалів та файли прогнозів із прив’язкою до attempt_id.
`validation_passed=false` не змінюється автоматично за одним показником.

## Планування та обмеження

`planning.Predictor.predict_correction(query)` і `predict_batch` повертають
вісім ймовірностей, похідні події, model_id/protocol_id та статус умов.
`load_predictor` читає зафіксований кандидат. Різні CRS, карта з іншим hash,
неперевірений домен або вихід за діапазони ознак мають явний статус без
вигаданої підстановки. Перевірка діапазонів не доводить сумісності домену.

`RasterReference` читає north-up RGB uint8 GeoTIFF і DEM у метричній системі;
масштабування Sentinel-2 не виконується неявно. `timed_route_queries` і
`saved_route_queries` задають спроби за інтервалом часу, а не кількістю клітинок.
Користувач явно задає геоприв’язку клітинок, камеру та попередню коваріацію;
модель одометрії не вигадується. MOA* не змінюється.

На українських AOI без кадрів і еталона можна перевірити тільки інтеграцію.
Перший прогноз нового українського домену буде позначено непідтримуваним,
поки немає окремої перевірки цього домену.

`opportunities.compare_opportunities` порівнює вибір однієї корекції за
U=P(Δe≥1)−P(Δe<−1) у заздалегідь визначених наборах. Усі predictions мають
бути вирівняні за attempt_id. Порівнюються geometry, random expected та,
якщо надано реальні map-only значення, наявна navigation metric. Відсутній
контроль позначається недоступним, не замінюється новою евристикою.
Вибір перевіряється на спостережених спробах, без твердження про кінцеву
похибку іншого польоту чи безпеку прибуття.
