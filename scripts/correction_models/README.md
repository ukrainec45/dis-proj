# Correction models — основний експеримент

Прогнозуємо **результат спроби корекції CAMP → RoMa → PnP до отримання майбутнього кадру**.
Локалізатор повертає координати та `accepted`; прогнозна модель — вісім імовірностей і можливі
похибки після корекції. Це різні компоненти. Локалізатор не адаптуємо до погіршеної видимості.

Новий пакет не імпортує попередній `correction_prediction`. Використовує незмінені компоненти
`scripts/visibility_localization`. Пошук маршрутів, VIO/INS і маршрутний GPU-експеримент не запускаються.

## Швидкий запуск

1. Скопіювати на Drive `scripts/correction_models` і `scripts/visibility_localization` зі збереженням структури проєкту.
   Стару папку експерименту переносити не потрібно. AnyVisLoc може бути в наявних ZIP-архівах.
2. Відкрити [01_collect_colab.ipynb](notebooks/01_collect_colab.ipynb), вибрати GPU runtime,
   встановити `PROJECT_ROOT`, `ARCHIVE_ROOT` до папки наявних ZIP і `DATASET_ROOT` для розпакування.
   Комірка автоматично знаходить і розпаковує сцени, без завантаження нових архівів. Повторний запуск
   використовує завершені розпакування. Уже розпакований датасет також підтримується.
3. Використати готову інвентаризацію та зафіксувати вибірку за офіційними сценами. Порожній старий
   geographic_audit не блокує роботу; reviewed=true не потрібне. Якщо немає 16 придатних груп, код
   повідомить дефіцит до завантаження зображень і моделей. Наявний inventory повторно сканувати не потрібно.
4. Перший запуск — одна нова спроба, після успіху — частини по 120. Наступний запуск пропускає завершені
   спроби. Після всіх 1920 з'явиться `results/main-v3-cusolver/dataset.json`. Це збір результатів, а не навчання CAMP/RoMa.
5. Відкрити [02_train_evaluate_cpu.ipynb](notebooks/02_train_evaluate_cpu.ipynb) у CPU runtime.
   Навчити, переглянути validation-звіт, потім увімкнути окремий фінальний тест.

**Чотирьох сцен недостатньо для основного дизайну.** Якщо вони незалежні й придатні, потрібно щонайменше
ще 12 сцен; за перекриття або нестачі кадрів — більше. Після додавання ZIP повторіть розпакування та
інвентаризацію. Новий склад сцен отримує окремі `inventory-<id>.json` і `geographic_audit-<id>.json`,
щоб не залишитися зі старим кешем чотирьох сцен. Зафіксована `selection.json` автоматично не розширюється.

Розпакування та інвентаризація не потребують GPU. ZIP залишається на місці, тому потрібен вільний простір
для розпакованих файлів. Підтримуються вкладені `Scene_XX/Lxx_reference.json` та плоскі `Scene_XX.zip`.
Пошкоджені архіви, небезпечні шляхи, дублікати сцен і конфліктні наявні файли викликають явну помилку.

Інвентаризація читає лише xyz/pose/euler: розмір кожного NPY-члена обмежений 64 KiB, форма й тип
перевіряються до виділення масиву. Зображення, карти й моделі тут не завантажуються. Вивід раз на
25 кадрів показує поточний файл, RSS процесу та доступну системну RAM. За залишку менш як 512 MiB
код зупиняється з MemoryError; це не гарантує захисту від зовнішнього скидання Colab.
Завершені сцени зберігаються в сусідній `inventory-<id>.scenes/`: після перезапуску повторіть
інвентаризацію з тими самими шляхами, без повторного розпакування. Кеш довіряє path/size/mtime;
при підготовці вибірки відібрані джерела додатково перевіряються та хешуються. Якщо RAM зростає,
збережіть останні рядки прогресу: без них причина збою конкретного Colab-сеансу не встановлена.

Якщо RAM різко зростає вже після першого рядка, не повторюйте повне сканування. У свіжому
Colab-сеансі після монтування Drive й налаштування шляхів виконайте:

```python
from scripts.correction_models.inventory_probe import probe_inventory
probe = probe_inventory(DATASET_ROOT, progress=lambda s: print(s, flush=True))
```

Це окремий процес Linux з лімітом адресного простору 3072 MiB, контролем RSS 1024 MiB,
доступної системної RAM 1536 MiB і часу 120 с. Перевіряється максимум 25 кадрів першої сцени,
друкуються початок/кінець кожного файлу та читання кожного metadata-члена NPZ. Повний inventory
не запускається, джерела й аудит не змінюються. Лог містить шлях і hash фактично імпортованого
selection.py, щоб виявити застарілу копію. Ліміт дочірнього процесу **не обмежує DriveFS**;
зупинка читача не гарантує звільнення кешів зовнішніх процесів. Успішні 25 кадрів не доводять
відсутність проблем на інших файлах. Для розбору потрібні останні рядки й підсумок probe.

### Перенесення з OneDrive без локального ПК

У першому ноутбуці є необов'язкова комірка **OneDrive → Colab → Google Drive**. Після монтування Drive
і налаштування ARCHIVE_ROOT увімкніть `DOWNLOAD_MISSING_SCENES=True`. Вона пропускає наявні сцени,
отримує посилання з офіційного порталу й завантажує відсутні ZIP до загальної кількості 16.
Перед розпакуванням вимкніть прапорець, якщо перенесення вже завершено.

Дані проходять через сервер Colab, а не диск вашого ПК. На Drive мають поміститися архіви та розпаковані дані.
Завантажувач `downloads.py` перевіряє ZIP перед публікацією і зберігає незавершений `.zip.part` після обриву.
Є до 8 спроб із паузами 2–30 с та HTTP Range; між спробами отримується свіжа адреса ZIP. Якщо зберігся
старий `.part` без checkpoint, перед дописуванням перевіряються останні 64 KiB перекриття, а після
завершення — CRC всього ZIP. У `.part.meta.json` зберігаються лише розмір і валідатори ETag/Last-Modified,
без адрес і токенів. Сильний ETag використовується з If-Range. Якщо сервер ігнорує Range та повертає 200,
частковий файл починається заново, щоб не дописати весь ZIP до вже наявного префікса.
Оновлення JSON не виправляє ConnectionResetError: це транспортний обрив, а не відмова доступу.
Не видаляйте `.part` після обриву; повторіть комірку. Не запускайте паралельних записів одного ZIP.
Успішний автоматичний доступ до порталу не підтверджений у цьому середовищі. Якщо OneDrive вимагає
авторизації (401/403), повтор тієї самої комірки не допоможе. У браузері відкрийте публічну папку авторів,
F12 → Network → очистіть список → оновіть сторінку та відкрийте каталог ZIP → Export HAR (sanitized)
з вмістом відповідей. Перенесіть невеликий HAR на свій Drive і задайте `ONEDRIVE_BROWSER_METADATA`.
Код читає явні адреси ZIP з метаданих. Повний JSON `RenderListDataAsStream` також підтримується:
`ListData.Row[].FileLeafRef` визначає назву, `.spItemUrl` — метадані файлу, а пара
`ListSchema[".driveUrl"]`/`[".driveAccessToken"]` надає тимчасовий доступ. Код створює авторизований
GET лише до метаданих файлу в тому самому drive; cookies та збережені заголовки запитів не копіюються.
Переадресація такого запиту заборонена, щоб не передати токен іншому серверу. Повернений сервером
`@content.downloadUrl` використовується для ZIP без додаткового заголовка авторизації.
`@content.downloadUrlNoAuth` не підміняє його: у перевіреній відповіді це URL без тимчасового параметра,
який повертав 401. Підтримується файловий домен `my.microsoftpersonalcontent.com`.
Цей спосіб відповідає використанню пар drive URL/token, описаному в [документації rclone](https://rclone.org/onedrive/#non-admin-access-to-business-onedrive).
Власний OneDrive для цього не потрібен. Наявність потрібних адрес у конкретному HAR не гарантована;
за їх відсутності буде явне повідомлення. Інший варіант — дозволені прямі HTTPS-посилання у `DIRECT_URLS`.
Посилання на сторінку папки не є адресою ZIP. Не вставляйте паролі/cookies
в ноутбук. Тимчасові downloadUrl не записуються у звіт.
Технічний вибір сцен для завантаження не замінює географічного аудиту та перевірки придатності кадрів.

HAR/каталог може містити тимчасові адреси й токени доступу: обробляйте його приватно, не публікуйте.
`one_drive_catalog.json`, `onedrive_catalog*.json` і HAR у корені пакета виключені з Git; файл не видаляється.
Це перенесення невеликого журналу запитів, а не завантаження ZIP на ПК. Якщо адреси спливли,
потрібно отримати свіжі метадані в браузері. API та браузерний доступ тут не є взаємозамінними.

Якщо після `pip install` ноутбук просить перезапуск: **Runtime → Restart session**,
`INSTALL_DEPENDENCIES=False`, виконати комірки зверху. `CUBLAS_WORKSPACE_CONFIG` встановлюється до CUDA.
`CAMP_CHECKPOINT=None` означає автоматичний кеш/офіційне завантаження, а не відсутню обов'язкову вагу.

Після відтвореного CUDA illegal-address збою RoMa на Scene_02/L02_0889 одиничний запуск із
пріоритетом cuSOLVER завершився без технічної помилки. Ініціалізація тепер явно встановлює
`torch.backends.cuda.preferred_linalg_library('cusolver')`; початковий smoke check також виконує
обернення батчу матриць. Це не гарантує працездатність усіх 1920 спроб і не встановлює остаточну
причину збою автоматично обраного backend. Математичний код RoMa залишається авторським.
Документований API: [PyTorch 2.14](https://docs.pytorch.org/docs/2.14/backends.html#torch.backends.cuda.preferred_linalg_library).
Версії Torch/CUDA, GPU, перевага бібліотеки й debug-прапорець заморожуються в `backend.cuda_execution`
у campaign manifest. Перед основним збором перезапустіть Python і приберіть діагностичну комірку
з `CUDA_LAUNCH_BLOCKING=1`: збір із цим прапорцем блокується до читання джерел.
Використовуйте нову OUTPUT `results/main-v3-cusolver`; старий запис технічної помилки збережіть.
SELECTION, inventory, сцени та ваги повторно використовуються; видаляти їх не потрібно.
Контрольні суми карт/DSM беруться зі спільного кешу `DATA/reference_fingerprints`, створеного
під час підготовки вибірки; нова OUTPUT сама по собі не змушує повторно читати всі карти.

## Вибірка і розбиття за сценами

160 знімків, по 10 просторово рознесених кадрів із 16 груп сцен. Greedy farthest-point
відбір використовує лише координати й геометрію, не результати локалізації. Seed 42.

| Частина | Території | Кадри | Спроби |
|---|---:|---:|---:|
| train | 8 | 80 | 960 |
| validation | 2 | 20 | 240 |
| calibration | 2 | 20 | 240 |
| test | 4 | 40 | 480 |

На кадр: σXY 5/20/50/100 м на вісь × clear/fog_extreme/smoke_extreme; один prior на рівень,
спільний між умовами. Чотири відкладені сцени — обмежена перевірка узагальнення, а 1920 спроб
не є 1920 незалежними знімками. Scene_05/07/08/11/21 вже переглядалися і не можуть бути тестовими.

Протокол `correction-models-v3-scene-disjoint` розділяє офіційні Scene_ID між частинами вибірки.
Глобальні координати AnyVisLoc навмисно приховані ([документація авторів](https://github.com/UAV-AVL/Benchmark/blob/main/docs/GROUND_TRUTH.md)).
Різні Scene_ID не доводять географічне неперекриття: у selection, campaign і звітах явно записуються
`geographic_overlap_verified=false` та `evaluation_scope=held_out_dataset_scenes`.

`audit-template` створює політику групування з неперевіреною географією. Старий порожній файл також
підтримується без reviewed=true і не переписується. Відомі спільні `spatial_group` зберігаються;
якщо задані `footprint_wgs84`, перекриття вимагають спільної групи. Точні дублікати aerial-карт
об'єднуються за SHA-256 перед фіксацією split, використовуючи контрольні суми джерел без декодування
зображень. Кеш відбитків довіряє path/size/mtime. Часткове візуальне перекриття не перевірене автоматично;
це записано в `map_overlap_check.partial_visual_overlap=not_verified`. Відсутність точних дублікатів
не є доказом географічної незалежності. Результат оцінює перенесення на відкладені сцени датасету.

У завантаженому inventory Scene_12 має 4 придатні кадри, тому доступні 15 придатних сцен.
Потрібна щонайменше ще одна придатна сцена; бюджет 160 кадрів/1920 спроб не зменшується.
Після додавання сцен новий inventory використовує кеш завершених сцен, читаючи лише нові/змінені.
Старі готові selection/model/dataset іншого протоколу не сумісні з v3; inventory та extraction receipts
зберігаються і повторно використовуються. Не перезаписуйте заморожені запуски: оберіть нові шляхи.

## Що вчиться модель

Вхід: карта навколо **неточного prior**, очікувана область огляду плюс 3σ, камера, невизначеність,
заданий сценарій видимості. Контекст 256×256 — наближення можливого спостереження, не точний майбутній кадр.
Справжній camera RGB, GT, реалізована prior-помилка, matches/inliers і конкретна маска диму входами не є.

Навчальні відповіді отримуємо запуском локалізатора на справжньому кадрі. Δe = e_before − e_after:

| Індекс | Клас | Δe, м |
|---|---|---|
| 0 | reject | корекція не застосовується |
| 1 | harm_large | < −20 |
| 2 | harm | [−20, −5) |
| 3 | harm_small | [−5, −1) |
| 4 | neutral | [−1, 1) |
| 5 | gain_small | [1, 5) |
| 6 | gain | [5, 20) |
| 7 | gain_large | ≥ 20 |

Пороги евристичні, не фізичні константи. Неперервні величини та XY-вектори зберігаються без обрізання.
Прийнята корекція замінює prior-позицію в цьому експерименті; це не перевірена схема злиття з VIO.

13 кандидатів: константа; logistic/forest × geometry/map/CAMP × зі сценарієм видимості/без нього.
Для CAMP-входу додаємо її незмінений опис карти до числових ознак. Семантичну перевагу такого опису
не припускаємо — перевіряємо на відкладених територіях. Порівняння з/без сценарію використовує однакові дані.

Ліс: 300 дерев, глибина 6, мінімальний листок 5. Logistic: C=1, стандартизація тільки train.
Листки лісу зберігають приклади з bootstrap-кратностями. Ваги прикладів визначають і класи, і похибки.
Logistic-контроль розподіляє масу рівномірно серед train-прикладів відповідного класу; константа має глобальний банк.
Вектор CAMP і геометрія не містять справжнього місця спостереження.

Для класу, відсутнього в train, Dirichlet +1 дає **апріорну**, не виміряну масу. Відповідного вектора
не вигадуємо: це `unresolved_outcome_mass`. Калібрування змінює ймовірності класів і узгоджено — ваги банку.
Це захищає від удаваної впевненості на кшталт «не було погіршень, отже ризик дорівнює нулю».

## Перевірка й артефакти

Вибір — мінімальний validation log loss; за рівності стабільний порядок від простіших моделей.
Температура підбирається лише на calibration, без повторного навчання на об'єднаних даних.
Фіксуються raw/calibrated моделі та їхні ідентифікатори. Фінальний тест не змінює вибір.

- Класи: log loss, Brier, conditional RPS, калібрування з кількістю спроб у кожному інтервалі.
- Похибка: CRPS радіуса, energy score XY, покриття односторонніх верхніх меж 50%/90%.
- Якщо є unresolved mass, повний proper score/межі не оголошуються визначеними. Окремо наводяться
  **діагностичні** оцінки розподілу, умовного на описаній прикладами частині. Вони не приховують невідомих хвостів.
- Окремі класифікаційні звіти за територіями/σ/умовами; парний cluster bootstrap за територіями.
- Окремий звіт незміненого локалізатора: прийняття, погіршення, похибки та парна різниця degraded−clear.

`models/*.json` — моделі без pickle; `frozen_run.json` — зафіксований вибір; `summary.json`, `scores.csv`,
`report.md` та PNG — звіти. Доступний приклад пакетного прогнозу в `prediction.py`.
`final_test_receipt.json` фіксує використання фінального тесту на рівні run, а не лише вихідної папки.
Не створюйте інший output для повторного підбору на тому самому тесті.

## Обчислення, відновлення та інтеграція

Профілювання вбудоване: затримка повної локалізації, кроки backend, GPU allocated/reserved peak,
RSS із кроком 20 мс. Короткі RSS-піки між відліками можуть бути пропущені. Завантаження reference та
ініціалізація записуються окремо; завантаження ваг мережею не є часом корекції.
У `sessions/` зберігаються ініціалізації, у `records/` — окремі спроби.

Кеші описів і фрагментів спільні між умовами. Перевірка великих reference-файлів кешується за шляхом,
розміром і mtime після SHA256-перевірки. Це довіряє файловим метаданим; для повної повторної перевірки
видаліть лише кеш `fingerprints/` при зупиненому зборі. Ваги та dataset не видаляйте.

Перша технічна помилка зберігає traceback і зупиняє збір. Повтор не перезаписує її. Після виправлення
конфігурації/коду використовуйте новий output: ідентифікатор протоколу не можна тихо змінити всередині run.
Незмінені код/конфігурація й кеш дозволяють продовження звичайних перерваних сеансів.

`RasterMap` читає вікна метричного north-up uint8 RGB GeoTIFF із DEM. Pyatka в EPSG:4326 потребує
окремого перепроєктування до метричної CRS. Нові українські карти автоматично не оголошуються перевіреним доменом.
Перевірка мінімумів/максимумів ознак не доводить спільну підтримку нових умов.
Для CAMP-прогнозів нові контексти потрібно закодувати незміненою мережею; CPU-кеш працює лише для точних збігів.

Синтетичні fog/smoke — sRGB-змішування, не фізична модель видимості в метрах. Навчання використовує
ізотропну горизонтальну невизначеність і фіксований профіль yaw/tilt/z. Немає доказу реальної погоди,
готовності Jetson, коректності послідовного накопичення похибки або ймовірності доставки.
Наукові підстави та межі новизни: [literature.md](literature.md).

## CLI та локальні перевірки

```text
python -m scripts.correction_models unpack ARCHIVE_ROOT DATASET_ROOT
python -m scripts.correction_models inventory DATASET_ROOT inventory.json
python -m scripts.correction_models audit-template inventory.json geographic_audit.json
python -m scripts.correction_models prepare inventory.json geographic_audit.json selection.json
python -m scripts.correction_models collect selection.json OUTPUT --runtime RUNTIME --max-new-attempts 120
python -m scripts.correction_models train OUTPUT/dataset.json RUN
python -m scripts.correction_models evaluate RUN OUTPUT/dataset.json FINAL_OUTPUT
python -m pytest scripts/correction_models/tests -q
```

Тести синтетичні, без мережі/GPU та без емпіричних наукових результатів. Не переносіть на Drive
локальні тестові папки й `__pycache__`. `results/`, `runtime/`, `model_cache/` і `data/` виключені з Git;
для відтворення експерименту архівуйте погоджені дані й артефакти окремо.
